# Investobot MVP — Financial Correctness, Single-Path Workflows, and Cleanroom Simplification

**Status:** Implementation-ready PRD · **Date:** 2026-10-13  
**Baseline:** [`mdbecker/investobot`](https://github.com/mdbecker/investobot), commit `304fa0c87c622288692d8ea6e8a60f93b49035b1`  
**Dependencies (assume completed before work starts):** `docs/PRD-unified-mvp-2026-10-10.md`, `docs/PRD-mvp-foundation-stabilization-2026-10-12.md`, `docs/PRD-mvp-wrap-up-2026-10-12.md`, and `docs/PRD-mvp-host-agent-docker-persistence-2026-10-12.md`. This PRD supersedes those documents **only where its explicit decisions differ**; all other established financial invariants remain in force.

## 1. Goal and decisions

Make the existing pre-user MVP trustworthy and maintainable for a long-term, mostly indexed-fund investor **before real portfolio use**. The host AI agent reads canonical host-accessible `skills/`, gathers permitted evidence, and invokes the deterministic CLI via `./scripts/invest` in Docker; SQLite contains accepted state; the loopback dashboard reads it without writes. The human reviews and manually executes any trades. Never move the agent into Docker, place instructions in a runtime prompt database, introduce a service/RPC/orchestrator, or require project packages on the host.

Prioritize financial correctness and one canonical implementation per financial rule over broad feature expansion. This is a cleanroom, no-user codebase: **delete** obsolete public commands, duplicated engines, tests and docs rather than writing compatibility adapters or data migrations. Retain the existing single Docker app/image, SQLite/Decimal accounting, immutable evidence and simulation, explicit human approval, typed uncertainty, and private bind-mounted `local-data/` state. No broker credentials, automatic orders, or background monitoring. **GitHub main-branch protection/required-check configuration is explicitly out of scope.**

The required scope is: (A) valuation/import/reconciliation correctness; (B) one source-aware fund look-through; (C) one estimated-sale tax calculation; (D) defensible multi-account actual performance; (E) one policy-governed planner and explicit writes; (F) minimal CLI/doc/skill cleanup; (G) real-source acceptance gates. Do not add new research families, optimization solvers, investment signals, new persistence engines, auth services, or large test/benchmark/fuzz frameworks.

## 2. Non-negotiable development sequence — BDD red before code

**Gate 0 happens first, across the entire PRD.** Before editing any production code, command wiring, canonical skills, or active documentation:

1. Write the **complete set of new/changed behavior scenarios** for work packages A–F in `.feature` files and matching pytest-bdd/public-CLI tests, with deterministic synthetic fixtures and independently calculated expected results. Assign each package its own test files. Cover success, partial evidence, blocked operations, idempotence, nonmutation, and relevant edge cases. Use observable Given/When/Then domain language; never test call counts, internal helper names, mocks of domain collaborators, or precise source layout.
2. Run the targeted new BDD suite in offline Docker at the unmodified baseline and capture **genuine failures with expected reasons** (assertion, mismatched status, missing command). Commit the red checkpoint before changing production code. Tests that already pass are preservation tests, not manufactured failures; investigate and document them rather than weakening a correct implementation. No `skip`, `xfail`, artificial exception, or intentionally invalid fixture to force red.
3. Only after all new scenarios have been written and red behavior verified may production changes begin. Implement A–E in the bounded ownership slices below, then F integration, then G validation. Turn each relevant scenario green; do not modify expected values merely to match the implementation. Refactor-only removals may use already-green public behavior tests plus a red test asserting retirement where behavior changes.
4. Finish with the full locked Docker pytest/ruff suites, actual CLI synthetic demo (adapted for retired commands), host bridge and read-only UI checks, offline skill packaging/install, and existing fixed-performance checks. Correctness takes precedence over optimizing benchmark medians. Record red/green evidence and the final exact commit; distinguish locally run results from GitHub CI.

### Minimum BDD behavior inventory (specific acceptance examples)

| Area | Given / When | Then observable result |
|---|---|---|
| A1 | A confirmed buy creates 2 shares without any current mark; request summary and look-through | Each reports `MISSING_VALUATION_MARK` and partial coverage; `total_value=null`, known subtotal remains visible, no invented price or mutation |
| A2 | A held security changes ticker but retains verified ISIN; reconcile a later complete snapshot | One canonical holding/lot identity, a ticker/alias change in the preview, **not** a fabricated liquidation and new investment |
| A3 | An import has a supported position plus provisional-adapter and unverified-lot warnings; reconcile | All parser issues survive with typed blocking semantics; eligible partial evidence may be accepted without being labeled fully verified |
| A4 | A partial snapshot omits a holding or a cash balance | Earlier unobserved holdings/cash are not erased or silently set to zero; incomplete coverage remains visible |
| B1 | A $1,000 fund source lists one identifiable 60% constituent and 40% undisclosed | $600 is displayed at the observed constituent level; $400 is unknown, never redistributed |
| B2 | Two funds disclose the same verified issuer through direct and nested paths | Canonical recursive exposure combines verified issuer amounts without losing account/fund contribution paths |
| B3 | Two funds disclose the same ticker **without** matching strong/verified issuer identity | They remain separate source observations; no invented cross-fund issuer aggregation; unresolved-identity amount is reported |
| B4 | Request current vs historical look-through with dated, stale, later-published and absent holdings | One calculation contract; current uses eligible persisted evidence and historical never uses evidence that was not available as of cutoff; stale/absent portions are typed, no silent provider refresh |
| C1 | Sell 3 of one lot and 2 of another, gross proceeds $500, adjusted bases $240/$140, total sale fee $5 | Total gain $115; term-specific gain and positive-tax-cost budget reflect **allocated fees** and preserve exact final fee residue |
| C2 | Loss-harvest and rebalance propose the same supported lot sale | The shared arithmetic returns the same estimated lot gains and conservative tax-budget consumption; legal wash-sale uncertainty remains an explicit review gate |
| D1 | Two accounts have full $1,000 and $2,000 close-date valuations one minute apart, with no intervening flows | A complete $3,000 household date checkpoint is available instead of two incomplete checkpoints |
| D2 | An external flow occurs between ambiguous same-day account valuations | No fabricated before/after household mark or TWR; typed chronology/flow-boundary issue explains required evidence |
| E1 | An approved policy and target permit a monthly cash-funded purchase | One deterministic, fee- and cash-floor-respecting proposal; accepted positions and marks are unchanged |
| E2 | An unapproved synthetic scenario is previewed; a real scenario lacks approved policy | Synthetic preview performs no write; real trade proposal is blocked; no second planning algorithm or alternate financial policy |
| E3 | A proposal embeds an unsaved target; an explicitly saved target ID is supplied instead | Embedded target is rejected without creating a target; saved target may be used for the proposal |
| F1 | Submit an immutable dataset manifest without/with explicit `--confirm` | First invocation validates/previews without writing; second saves exactly the approved manifest; repeated identical submissions are idempotent |
| F2 | Compare backtests or list proposed plans | Comparison never silently creates target versions or transition plans; saved artifacts are explicitly identified; full proposal has executable quantities, lot IDs, estimated fees and tax caveats |
| F3 | Recent trades already occurred this month; agent plans a routine contribution | Skill reports timing/preferences and prefers contributions-only; no hard calendar prohibition prevents a justified exception |

Use additional small scenarios where necessary to show incompatible precision, ambiguous identities, unresolved accounts, stale source dates, account-specific cash, fee residues, and preservation of existing recovery safeguards. A green suite that never fails when the behavior is removed is not adequate evidence.

## 3. Implementation work packages — minimal overlap

**Package A — Observation, identity and valuation safety (priority: must fix).**  
**Owner files:** `src/invest/ledger.py`, `src/invest/parsers/generic.py`, `src/invest/portfolio_summary.py`, shared observation models only if unavoidable; tests `tests/features/mvp/observation_correctness.feature` and `tests/test_mvp_observation_correctness_bdd.py`.

- Treat absent current marks consistently: never run `Decimal(None)`, never invent a price or equate unknown to zero. Return a typed partial result, `total_value: null`, and `known_value_subtotal`; ratios requiring unknown full-household denominators are `null` rather than misleading percentages. Keep genuine independently known subtotals.
- Reconcile by canonical security identity (reviewed strong IDs/aliases) **before** presenting differences or applying positions/lots; reuse the same resolved identities in preview and acceptance. A ticker update is metadata, not an implicit sale. Ambiguous or conflicting strong IDs block atomically. Do not make ticker alone a verified issuer match.
- Carry every parser issue into reconciliation. Separate `blocks_acceptance`, `blocks_calculation`, `blocks_proposals`, and `blocks_execution_review`; preserve unverified/provisional source diagnostics without automatically treating all as fatal. Incomplete snapshots must not delete unobserved inventory or cash. Existing account settings remain authoritative.
- Keep accepted activity, source timestamps, stable confirmed lot identities, and idempotency untouched. No schema change unless a proven behavioral invariant cannot otherwise be represented.

**Package B — One recursive, evidence-aware look-through (priority: must fix).**  
**Owner files:** `src/invest/lookthrough.py`, `src/invest/portfolio_research_inputs.py`, `src/invest/analytics.py` (exposure only), source adapters in `src/invest/market.py` only as required; tests `tests/features/mvp/exposure_consistency.feature` and `tests/test_mvp_exposure_consistency_bdd.py`. **Do not edit `cli.py` in this package.**

- `lookthrough.exposure` is the **single canonical numeric engine** for household and research look-through. Delete the separate exposure calculation in `analytics.py` after its callers are switched. Preserve recursive funds, known weights, cash, source paths, cycle/depth protection, currencies, source dates, and independent numeric versus evidence completeness. Historical calls remain point-in-time safe.
- A constituent can have a source-backed **observed identity** without being a registered canonical security. Keep its numeric weight, source label/identifier, and original fund path in an exploratory exposure row. Unmatched source identities must not silently disappear. **Never auto-register thousands of constituents** or claim that equal tickers/names prove equal issuers.
- Merge constituents across funds and into issuer-level company totals **only** when canonical/verified strong issuer identity permits it. Distinct unverified source records remain separate and contribute to `unresolved_identity_value`, **not** to undisclosed `unknown_exposure_value` (which tracks weights not represented at all). Source weights summing above 100% block that observation, not inflate exposures. Show dates/evidence quality and known numeric amount even where research/trades remain blocked.
- `portfolio exposure` uses persisted observations through this engine; no network calls or cache writes during exposure. Omitted `--as-of` means current UTC reporting date; supplied `--as-of` means historical cutoff. Pinned immutable holdings take precedence. Eligible persisted provider caches may support **labeled provisional current exploration only**, never backdated historical claims or authoritative issuer equivalence. Provider retrieval remains an explicit `fund holdings` operation, separate from exposure. Research-universe selection consumes verified issuer rows from the same result and retains unresolved/filtered coverage.
- Preserve a stable shared response shape: `status`, `as_of`, `total_value`, `known_value_subtotal`, `exposures`, `unknown_exposure_value`, `unresolved_identity_value`, `stale_exposure_value`, `issues`, provenance/contribution paths and evidence-completeness flags. Coverage percentages use a known complete denominator or are `null`.

**Package C — Single sale-gain and tax-cost rule (priority: must fix).**  
**Owner files:** `src/invest/tax.py`, `src/invest/tax_policy.py`, `src/invest/harvest_proposals.py`; coordinate exactly one small pure calculation reused by `planning.py` in Package E; tests `tests/features/mvp/sale_estimates.feature` and `tests/test_mvp_sale_estimates_bdd.py`.

- Define a single plain-function Decimal calculation for **hypothetical** specific-lot sales: allocate explicit sale fee over selected quantities, give final residue to the last lot, use current **remaining adjusted basis**, compute each lot's realized gain = `quantity * sale_price − basis_removed − allocated_fee`, derive term from acquisition/sale dates, and compute conservative positive gain tax cost = `max(0, gain) * approved term rate` per lot. Do not reconstruct executed sale facts from today's remaining lots.
- Wire approved rebalance and conditional TLH estimations through it; keep confirmed executions using their immutable recorded allocations and the existing execution accounting rules. Identical hypothetical lot/fee inputs must yield consistent budget and report numbers across workflows.
- Positive estimated tax costs consume annual allowance; losses **do not replenish** it. Never claim definitive tax liability, guaranteed savings or wash-sale safety. Preserve unknown spouse/IRA/DRIP/outside-account, substantially-identical and future-purchase review gates.

**Package D — Accurate household performance dates (priority: must fix).**  
**Owner files:** `src/invest/performance_ledger.py` and (only if necessary) `src/invest/performance.py`; tests `tests/features/mvp/household_performance_dates.feature` and `tests/test_mvp_household_performance_dates_bdd.py`.

- Assemble candidate household valuation checkpoints by **reporting calendar date**, rather than requiring identical timestamp strings across accounts. A complete household checkpoint needs one compatible valuation for every selected account and known cash/position coverage; ordinary minute-separated same-date valuations with no intervening flows may combine.
- When a flow occurs on the date, identify before/after using explicit source and confirmed event timestamps. If account observations are on incompatible sides of a flow, have conflicting same-date values, are date-only where ordering matters, or cannot establish a common boundary, return a typed ambiguity/missing-boundary issue instead of synthesizing a checkpoint.
- Keep actual TWR/XIRR/CAGR independent of hypothetical backtests. Do not infer missing cash flows from balance differences, infer market-close times, or modify historical accepted state.

**Package E — One planner and no implicit accepted writes (priority: should fix now).**  
**Owner files:** `src/invest/planning.py`, `src/invest/plans.py`, `src/invest/plan_storage.py` as needed; **retire** `src/invest/proposal_generation.py` after callers and tests are converted; tests `tests/features/mvp/planning_single_path.feature` and `tests/test_mvp_planning_single_path_bdd.py`. **Do not edit `cli.py` in this package.**

- `planning.propose` is the **only** investment-action generator for contributions-only and rebalance, in synthetic and real modes. A saved **approved immutable policy ID is mandatory** for real proposals. Synthetic exploratory preview uses the exact same engine with explicitly synthetic unapproved assumptions; it saves **nothing**. Approved proposals may save an immutable hypothetical plan but never alter accepted positions, cash, lots, quotes, or approved policy.
- Retire the synthetic-only `plan generate` public path, its engine, redundant gain-budget interpretation and implementation-specific tests/docs. Keep useful synthetic scenario behavior using a read-only `plan preview` command (wired in Package F); do not create a second algorithm, scheduler, optimizer, or compatibility alias. Both modes use conservative annual positive estimated tax-dollar allowances, never parallel ST/LT realized-gain-budget rules.
- Real `plan propose` requires a **previously saved target ID**, never an inline target dictionary that secretly writes target versions. Save/activate targets and approve policies using their distinct explicit commands. Keep deterministic account/cash-first allocation, verified sale lots, exact increments, floors, permissions, unknown fees, stale evidence, and human review. Never present greedy planning as globally optimal.
- Backtest comparison remains an immutable hypothetical run/compare operation. **Remove its implicit target-version creation and transition-plan generation**; the host agent may explicitly save a selected target and then call `plan propose` to get a transition. Preserve saved historical run content and assumptions.

**Package F — CLI integration, ergonomics, skills and documentation (priority: should fix now).**  
**Exclusive owner:** `src/invest/cli.py`, CLI discovery descriptors, `src/invest/db.py` one-line cleanup, `skills/`, current `README.md`, `AGENTS.md`, `docs/architecture.md`, `docs/workflows.md`, `docs/agent-usage.md`, `docs/trading-policy.md`, `docs/lookthrough.md`, `docs/skills.md`, `docs/testing.md` and related current docs; tests `tests/features/mvp/public_cli_contracts.feature` and `tests/test_mvp_public_cli_contracts_bdd.py`.

- Wire the domain packages into one CLI contract. Retire `plan generate`; expose **read-only** `plan preview --file FILE --target TARGET_ID --as-of DATE` for explicitly synthetic, unapproved policy/price inputs; keep `plan propose --file FILE --policy POLICY_ID --mode MODE --as-of DATE` for saved, approved hypothetical plans. Both use the same underlying planner and return complete internally consistent action detail (including account, canonical security, units, price, notional, fees and selected lot IDs). Do not strip the detail from saved `plan show` or trade-plan reports. Keep the existing tool/schema discovery accurate.
- `data snapshot --file FILE` means validate/preview, `data snapshot --file FILE --confirm` publishes. Confirmation required for accepted research/data evidence; labeled creation of hypothetical plans/backtest runs is allowed without that same gate. Repeat of an identical published immutable artifact is idempotent. Never allow UI write methods; dashboard stays GET-only/query-only and broker/provider-free.
- Remove redundant CLI paths, leftover `INVEST_PROMPTS` test setup, stale prose and duplicated command examples. Rename the `db.connect(initialize=...)` shadowing flag internally and call `initialize()` normally; no host or database migration. Do **not** perform a wholesale CLI/framework rewrite: only extract a cohesive command group if removal/reworking leaves an obviously clearer module; no arbitrary line-count target.
- Keep one authoritative tested operational walkthrough in `docs/workflows.md`; README, skills and other docs link to it instead of copying stale flags. Ensure the README still explains that skills live/read **on the host** and only deterministic commands and the viewer run in Docker. Keep current PRDs discoverable and explicitly mark superseded historical setup instructions.
- Update monthly-investing/strategy/rebalancing skills to **prefer one routine discretionary trading session per month and at most four rebalances per year**, using confirmed recent activity as context. This is an **agent preference**, never a hard CLI/date restriction: necessary trades may be proposed on any valid date with an explicit explanation. Prefer new cash over taxable sales; no automatic execution or future scheduler. Keep skills composable primitives rather than writing long duplicated workflows.

**Package G — Final real-world readiness gate (priority: must fix before live use).**  
**Owner:** acceptance evidence and small, sanitized fixture/test additions; no production redesign unless a concrete failing real-source scenario demands it.

- Once the behavioral suite is green, test **human-reviewed, permission-cleared sanitized samples** from Vanguard, Fidelity NetBenefits 401(k), and PNC, plus entitled actual FMP responses. Independently document expected positions, dates, cash, precision, stable lot identity/adjusted basis, source freshness, and coverage. Do not fabricate sample coverage or persist raw financial HTML in Git. Until these inputs are supplied, leave each adapter/provider explicitly `PROVISIONAL`/`UNVERIFIED`; this external human gate cannot be marked passed by synthetic CI.
- Validate an end-to-end import → reconcile → explicit acceptance → subsequent snapshot → confirmed activity/lot lifecycle → actual-performance or typed blockers → sourced fund exposure → contributions-only/rebalance/TLH **conditional** proposal → backup/restore. Test that previews, reports, backtests and read-only UI do not mutate accepted facts. Preserve human review and manual trade execution.
- Record a compact readiness matrix per source/workflow: **VERIFIED**, **BLOCKED** (with typed reason), or **NOT TESTED**. A source is not verified because a test passes against fictional HTML. No public market-data API credentials or private originals in tests/logs.

## 4. Integration ownership and acceptance

A–D own separate domain modules; E owns the planner; **F alone edits `cli.py`, shared command discovery and documentation** after A–E interfaces stabilize. If a shared model/validator must change, appoint one coordinator, announce the contract, and avoid simultaneous edits. Test owners use the separately named feature/pytest files above; the coordinator updates existing regression tests and demo flows only after the initial all-red checkpoint. Merge in dependency order **A/B/C/D → E → F → G**. Each package runs its changed scenarios and adjacent existing scenarios; full-suite integration belongs to F/G.

The final acceptance requires: (1) all new observable BDD scenarios green after genuine prior red evidence; (2) existing financial invariants and full locked Docker tests green; (3) no duplicated exposure or proposal engines/retired public commands; (4) no unexpected accepted-state mutations, invented money/identity/chronology, or silent missing-data normalization; (5) consistent CLI/skills/read-only dashboard/docs; (6) successful actual offline CLI demo, skill installation, backup/restore and performance checks; (7) explicit **unverified** labels on any real-provider gates that lack reviewed evidence. Do not claim real-trade readiness until G is genuinely verified.

### Review standard for the implementing developer

Use the attached `code_review(8).md` and `code_smell_review(9).md` as review criteria: **intent → architecture → implementation → polish**, with special attention to Bloaters, Change Preventers, Dispensables, Couplers, Python error/state smells, and tests coupled to internals. Evaluate each change by correctness, actual future maintenance cost and observable behavior. Remove accidental duplication/dead code before adding abstractions; do not add speculative generality, internal mocks, parallel policies, excessive documentation, backward-compatibility layers, schema churn or an agent service. Label important review findings **Must fix before merging / Should fix now / Recommended now / Can defer** and **TODO / Question / Follow-up / Nit**. The target is the simplest complete working product, **not** maximal defensive machinery or smallest diff.
