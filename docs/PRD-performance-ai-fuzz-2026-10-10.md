# Investobot — Performance Coverage, Regression Gates & Optimization PRD

**Status:** Separate post-MVP implementation PRD · **Date:** 2026-10-10 · **Priority:** P1, required before the rebuilt MVP is considered performance-stable.

**DEPENDENCY — ASSUMED COMPLETE BEFORE STARTING:** **Investobot — Unified MVP Rebuild PRD** (`investobot_unified_mvp_prd_2026-10-10.md`), all WP00–WP12, including the new SQLite ledger, DuckDB/Parquet analytics, portfolio workflows, research corpus/vector search, seven agent skills, and its green BDD/CI release gate. Preserve its financial correctness, provenance, permissions, and architecture. This PRD **supersedes only** the Unified PRD's *observational-only performance testing / ≤2× regression* policy: the gates below are stricter. Historical PRDs remain preserved. If the Unified MVP is not complete, do not fabricate baselines against features that do not exist; finish it first.

## 1. Objective and explicit decisions

Deliver a compact, fully offline, Docker-based performance suite that **benchmarks 100% of the identified performance-critical user paths** (inventory in §3), detects material regressions in CI, and **requires fixes for observed slow operations before acceptance**. The tests must both identify *where* time/memory/storage is spent and stop slower changes from silently reaching `main`.

- **Regression threshold:** **fail when candidate median elapsed time exceeds either comparator by more than 25%** for any required benchmark case. Also fail for **>25% peak RSS**, **>25% persisted output/DB growth**, or **>25% temporary disk usage** for the same logical workload when that metric is relevant and reproducibly measured. On extended/nightly *retrieval* cases with ≥21 observations, also fail if p95 elapsed time grows **>35%**. Comparison is strictly `candidate / comparator > 1.25` (or `>1.35` for p95), not a rounded displayed percentage. A tie at the threshold passes.
- **Comparators:** On every pull request, run the **candidate against (a) the PR's current target-branch commit** (catches a new slowdown) and **(b) the immutable, reviewed post-MVP performance reference commit** (catches cumulative slowdown). Run all three on the **same CI runner** using the same fixed data and resource limits, not against wall-clock numbers taken on another machine. The archived JSON of reference measurements is audit evidence, **not** the cross-machine timing gate. After merging to `main`, compare against the immediately prior `main` commit and the pinned reference. No automatic baseline reset or threshold widening.
- **KISS:** Use `time.perf_counter_ns`, Python stdlib, existing pytest/pytest-bdd, disposable real SQLite, real DuckDB/Parquet and real sqlite-vec. A small `scripts/perf.py` runner, a checked-in `benchmarks/cases.json`, a checked-in `benchmarks/reference.json`, a few BDD feature/step files, and one GitHub Actions job are enough. No benchmark SaaS, database server, telemetry, continuous daemon, profiling framework, Prometheus, or third-party benchmarking dependency.
- **Coverage meaning:** All known potentially slow, high-volume CLI workflows and their important storage/analysis paths must have named measured cases, including failure/blocked data scenarios where expensive processing is involved. This is **100% workload-inventory coverage**, not a false claim of 100% CPU instruction, line, branch, all input combinations, or future undiscovered hot paths. The coverage validator must fail for any required case absent from the runnable suite. A new expensive command/path must add a case in the same change; a cheap command can be explicitly exempted with a short, reviewed reason.
- **Safety:** Measure only synthetic, fixed-seed and reproducibly generated datasets in disposable Docker containers with `--network none`. Never mount, benchmark, copy or profile a user's real ledger, research, credentials or Docker data volume. Benchmarks may not mutate financial truth except inside isolated disposable fixtures; final output consistency checks are mandatory.

## 2. Benchmark contract and CI policy

**Deterministic inputs.** Build synthetic inputs once from a pinned seed (`271828`), fixed UTC dates, canonical decimal strings and immutable scenario definitions. Check fixture recipe version and SHA-256 in `benchmarks/reference.json`; materialized large fixtures are generated locally from recipes, not committed as multi-gigabyte blobs. Source/provider/browser calls are stubbed **only at external boundaries**; use real in-process algorithms, CLI JSON serialization, transactions, indexes and local file I/O. For every case, specify: `id`, workflow/entry point, fixture profile, measured operation boundary, whether it mutates, repetitions, tracked metrics, expected result/coverage invariant, and scalability partner. Fail a case whose output is wrong, omitted, partial when complete was required, or inconsistent with its independent behavioral fixture, **even if it is fast**. Do not optimize by skipping work or lowering data coverage.

**Execution.** Both source revisions run with their own *locked* Docker dependencies, same fixture recipe/input hashes, no network, Linux x86-64, one warm-up, `--cpus=2 --memory=4g`, `OMP_NUM_THREADS=1`, `OPENBLAS_NUM_THREADS=1`, `MKL_NUM_THREADS=1`, and one benchmark process at a time. Build/image startup, fixture generation and initial fixture seeding are excluded unless that operation is itself the named case. An explicitly named CLI startup case includes process startup but not `docker run` or Docker build. Use a separate frozen copy of input state for **each timed mutation**; no repeated run may accumulate new plans, rows, cache state or WAL growth from prior repetitions. For read operations document warm-process/data-cache expectations; do **not** falsely label a result “cold OS cache” unless tested with an actual verified cold cache.

**Statistical rule.** PR suite: interleave reference/base/candidate in rotated order, collect **seven timed values per revision per case** after warm-up, report median and max; time each operation or a documented batch of repetitions large enough to take ≥200 ms so timer noise does not dominate. Extended suite: **21 observations** for query/interactive cases (report p50/p95); **three observations** for slow bulk mutations/index rebuilds (report median only and explicitly `p95: null`). Use the same order schedule for all revisions. Compare raw medians, not one lucky run or a best-case minimum. Record elapsed time, maximum resident set size, relevant process exit code, disk artifacts/WAL/temp/spill bytes, data counts, output hash/status, source commits, fixture hash, Docker/dependency versions and CPU/memory limits as JSON. Peak RSS must use a fresh process per timed observation, not cumulative `resource.getrusage` of a long-lived orchestrator. Storage comparisons include SQLite data/WAL at a defined checkpoint state and referenced Parquet/index bytes; explicitly exclude generated benchmark logs.

**Noise/retry.** If a threshold is exceeded, the CI job **must fail provisionally** and execute **one complete fresh paired measurement** for that failed case on the same runner after an idle/cooling interval. The job fails if the fresh pair also breaches the threshold, or if either run errors/has incorrect output. A passing retry is recorded as `NOISY_FIRST_MEASUREMENT`, not silently discarded; repeated noisy cases must be fixed (isolate the benchmark or increase batch work) before release. No manual `skip`, `xfail`, automatic baseline rewrite, or “expected slowdown” switch in PR CI.

**Absolute slowness:** A new suite might establish a perfectly consistent but **slow** reference. Therefore initial certification also applies these defined user-experience budgets on a **documented laptop-class or equivalently constrained 2-vCPU/4-GiB reference runner**: routine interactive read/preflight/plan list/search **≤2 s p95**; 1,000-position import/reconcile and actual performance **≤5 s p95**; 1,000-position proposal, harvest plan, look-through and top-issuer aggregation **≤10 s p95**; 10-year/three-target backtest and 500k-row historical analytic query **≤30 s** per run; 100k-chunk top-10 vector search **≤2 s p95**; 100k-chunk vector-index rebuild **≤180 s**; backup+verification or restore of a 200-MiB fixture **≤120 s**. Treat these as **engineering budgets, not historical measurement claims**. CI's primary relative gate is the portable merge guard; certify absolute budgets on the constrained documented runner during initialization and before releases. When a budget fails, optimize and rerun until it passes; do not bless a slow reference.

**Growth guard.** For the designated scaling pairs in §3, compare 1× vs 4× logical records on the **same code revision**. For workloads expected to be approximately linear (indexed reads, ledger import/reconcile, lot/tax scans, look-through, Parquet scans, research aggregation), fail if `T(4×)/T(1×) > 6.0` after batch overhead is controlled. Exempt inherently nonlinear algorithms only if the case explicitly documents expected mathematical complexity and an alternative measured upper bound. Do not introduce a 6× exception casually just because current code is quadratic. All scaling case data counts and coverage must match the defined profiles.

**Required development order:** First verify the Unified MVP's ordinary tests and Ruff are green on the known commit. Then, **before writing any production code or performance runner implementation**, add *all* feature scenarios, step definitions, test fixture contracts and required-case manifest entries. A behavior that already exists may be marked as an existing passing guard, but never manufactured into failure by changing expectations; every *new missing* requirement must be red first. No `skip`/`xfail`/nonfunctional dummy measurement is permitted.

Each scenario uses `Given / When / Then` language describing observable results; do not assert internal method calls. Minimum cases:

| BDD ID | Observable scenario (one behavior per case) |
|---|---|
| **PERF-01** | **Given** the published critical-workflow inventory, **when** coverage is checked, **then** every P01–P15 subcase has a runnable benchmark and no expensive public workflow is unclassified. |

# Investobot — Agent-Driven Exploratory Fuzzing Addendum

**Date:** 2026-10-10 · **Status:** Addendum to *Investobot — Performance Coverage, Regression Gates & Optimization PRD* (`investobot_performance_regression_prd_2026-10-10.md`).

**DEPENDENCIES — ASSUME COMPLETE:** The *Unified MVP Rebuild PRD* (WP00–WP12) and the *Performance Coverage, Regression Gates & Optimization PRD* (W0–W4), including the P01–P15 critical-path inventory, deterministic CI benchmarks and its >25% median regression gate. This addendum does **not** change those gates or the application's architecture. Implement it afterward. Its unmet BDD scenarios must be committed and observed **red before any fuzz harness or product implementation** begins.

## 1. Objective and boundary

Provide an **on-demand, AI-agent-driven exploratory fuzzing workflow** that discovers correctness, accounting, data-integrity, input-validation and performance bugs in Investobot; produces compact, exact, actionable bug reports; and converts confirmed discoveries into ordinary deterministic regression tests and fixed performance benchmarks.

**Non-negotiable: exploratory fuzz campaigns DO NOT run in CI.** No GitHub Actions fuzz job, required fuzz status check, cron/nightly fuzz trigger, hosted LLM/API key, scheduled campaign or CI access to an AI agent. The human explicitly tells their **existing local coding agent** to run a new fuzz campaign. The agent devises meaningfully new scenarios every time, invokes the local harness, investigates findings, and reports them. CI runs **only** the performance PRD's fixed P01–P15 benchmarks, conventional BDD/unit/integration tests, and deterministic regression cases distilled from prior discoveries. Deterministic tests of the *fuzz harness itself* may run in CI, but **no AI-generated campaign execution** may run there.

**Determinism boundary:** New exploration must vary between campaigns; any individual discovered case must be exactly replayable *without an AI*. The model proposes test inputs and hypotheses; independent, version-controlled Python oracles determine correctness. Never treat model-authored expected numbers, explanations or test code as a source of truth.

**KISS architecture:** One agent instruction file (`docs/agent-fuzzing.md`), one small Python entry point (`scripts/fuzz.py`), a typed allowlisted scenario schema, focused fixture generators/oracles, and optional development-only **Hypothesis** for shrinking/value generation. Reuse pytest/pytest-bdd, existing domain models, real temporary SQLite/DuckDB/Parquet/vector implementations and the performance PRD's benchmark runner. No autonomous LLM service, plugin, new server, queue, telemetry, external bug tracker integration or second performance framework.

## 2. How one campaign works

1. **Explicit human invocation.** The user tells the available coding agent, e.g., *“Run a fresh Investobot fuzz campaign emphasizing accounting, tax planning and expensive queries; report and reproduce every issue.”* The agent reads the CLI schema (`invest tools list/describe`), changed modules, the benchmark inventory, prior local fuzz reports and the allowlisted scenario contract. Nothing runs automatically merely because a commit or PR exists.
2. **AI designs fresh cases.** The agent creates **at least 12 distinct scenarios** per campaign spanning **at least five** P01–P15 families, prioritizing code changed since the last campaign, previously underexplored families and plausible adversarial edge cases. It must vary **workflow families, action ordering, cross-record relationships, invalid inputs, numeric boundaries, data sizes and failure modes**. Changing only PRNG seeds, names or cosmetic parameters is not enough. At least four cases must be multi-step state transitions; at least two must target performance or pathological growth. Within five recorded campaigns, the agent must cover all P01–P15 families; missing families are reported as coverage gaps, not silently marked covered. Campaign size may be raised explicitly by the human, but never automatically by CI.
3. **Machine-enforced novelty.** The harness derives a canonical `input_hash` from the *fully executable* case including seed and exact values, and a `shape_hash` from family + operations + ordered transitions + perturbation categories, excluding incidental IDs, values, dates and seed. It rejects any repeated `input_hash` across the current campaign and retained local history, and requires **at least 25% of scenarios to have a `shape_hash` absent from the previous ten campaigns** (or all available history during bootstrap). The agent revises its proposals until accepted; if it cannot, the campaign fails explicitly with a novelty report rather than rerunning old cases. This guarantees recorded novelty, not exhaustive coverage of the input universe. Record the local run history under an **ignored** private application-data directory; include a portable sanitized export/import of history so novelty survives rebuilding a laptop. First run starts with an explicit empty history; accidental missing later history is a warning requiring human acknowledgment, not a silent reset.
4. **Strict generation interface.** The agent writes data, **not executable tests**: versioned JSON scenarios using allowlisted operation names (import, reconcile, apply, activity, tax, plan, query, backup, research, backtest, vector, etc.), typed parameters, scenario seed, synthetic fixture profile, mutations, independent invariant IDs, expected *result class* and the intended performance dimension. Reject unknown operations/fields, paths, URLs, SQL/Python/shell snippets, unbounded inputs, unsupported prerequisites, or assertions outside the registry. Free-text case rationales cannot control execution. Defaults: at most 12 operations, 25,000 records and 20 MiB compressed input per scenario; larger intentionally stressed cases require an explicit local `--large` option and tighter memory/time guards.
5. **Validate and execute locally.** The agent invokes `python scripts/fuzz.py validate CASES.json` followed by `python scripts/fuzz.py run CASES.json` **inside the project's disposable, network-disabled Docker runtime**, never against the user's portfolio DB, mounted private account files, brokerage credentials or live FMP data. Each scenario gets a clean isolated database/filesystem and deterministic synthetic clock/market/provider data. The harness sets per-case CPU, RAM, disk and wall-time limits, records OOM/timeouts rather than swallowing them, and does not allow generated input to escape its temporary directory. Run all application commands through the real public CLI/domain boundary, not mocks of financial internals.
6. **Independent oracles and shrinking.** Check portfolio accounting conservation, position/lot/cash/basis consistency, immutable provenance, idempotent replay, same-state recomputation, ordered versus reordered equivalent inputs, supported error codes, absence of partial writes on rejected input, no look-ahead in backtests, no invalid trading under incomplete facts, vector filter correctness, saved research continuity and missing-data propagation. Compare small exact financial examples with an independent decimal reference implementation; for other cases use invariants/metamorphic relations (e.g., reordering independent import rows must not change accepted financial results). Hypothesis may shrink numeric/stateful examples; persist the smallest verified failing **complete runnable sequence**, not just a stack trace. Expected validation errors are passes only when the correct status is returned and state is unchanged.
7. **Report and triage.** The harness writes a local, sanitized `fuzz-report.md` and `fuzz-report.json` for each campaign, with case ID, input/shape hash, family, expected versus observed behavior, violated invariant, exact saved fixture, minimized sequence, seed, source commit/dirty-tree fingerprint, locked dependencies, stdout/stderr, resource measurements and an **agent-free replay command**. The agent investigates and labels issues `CONFIRMED_BUG`, `CONFIRMED_SLOW_PATH`, `EXPECTED_REJECTION`, `UNCONFIRMED` or `ENVIRONMENTAL`, with a short explanation. A finding is confirmed only if the saved case reproduces at least **twice** from clean state. Group repeats by normalized failure signature; never fabricate separate bugs merely because different seeds hit the same defect. Reports remain local by default; optionally the agent may draft a GitHub issue, but creating/publishing one requires the user's explicit request or approval. The campaign must exit nonzero on confirmed bugs and unresolved execution/contract failures; unexpected bugs are never silently skipped.
8. **Fix, preserve and rerun.** For each confirmed bug, create a **minimal Given/When/Then BDD regression scenario**, execute it to observe the expected **red**, then make the smallest targeted production change and verify green, followed by affected existing behavioral/performance tests. Archive the original fuzz input for forensic replay. CI subsequently executes the new **fixed** regression test as part of the conventional suite; it does *not* launch the agent or a fuzz campaign. Do not modify financial rules to make a fuzz test pass unless the PRD explicitly permits the behavior.

### Agent entry contract

Provide a concise copyable instruction in `docs/agent-fuzzing.md` requiring the local coding agent to: inspect recent code changes, previously attempted scenario shapes and P01–P15 gaps; invent structurally fresh cases; write schema-valid JSON; run the safe offline harness; retry invalid/duplicate proposals; minimize/replay suspected defects; produce ranked bug reports; and ask permission **before** modifying production code or publishing external issues. The agent may use its existing IDE/repository tools. **Do not hard-code Codex CLI, Claude Code, an API vendor or a new credential into Investobot.** The runner never launches an LLM itself.

## 3. Performance-specific fuzzing

Dynamic fuzzing should search for unexpected complexity and pathological inputs, not compete with the stable statistical CI suite.

- Agent-generated cases vary tax-lot counts, import row ordering, competing fund aliases, fund-of-fund depth, duplicate issuer mappings, large historical windows, missing date distributions, plan alternative counts, repeated research updates, compressed Parquet row groups and vector filter/selectivity patterns. Capture operation-level time, peak RSS, DB/WAL/Parquet/index bytes, peak temp storage and logical data counts.
- The fuzz harness detects *suspects*: timeout/OOM, the performance PRD's **absolute user-experience budget** breached on an equivalently constrained local runner, or unexpectedly worse growth between **the same generated case at 1× and 4× input size** (default flag when time growth exceeds **6×** for a nominally linear operation). Do **not** compare raw elapsed times from two different AI-generated inputs and call that a regression.
- For a suspected regression, save an exact immutable case. Optionally use the performance PRD's existing runner to execute **the same case** against the candidate and known-good code on the **same local machine/limits**, with seven timed observations per revision, one fresh paired retry on failure, and the existing **>25% median** rule. Label `CONFIRMED_SLOW_PATH` when the 25% breach repeats, or when an absolute budget/scaling failure is reproduced; otherwise report as a suspected/measurement-noise finding. This **local investigation does not create a CI fuzz job**.
- Profile confirmed slow paths with `cProfile`, SQLite `EXPLAIN QUERY PLAN`, DuckDB `EXPLAIN ANALYZE` or relevant vector profiling. Fix the smallest measured bottleneck while preserving identical outputs. Add the minimized, **fixed-input** performance case to `benchmarks/cases.json` when it reveals a new critical workload, so **future CI runs measure that deterministic case** under the original 25% gate. Add a corresponding red-first BDD behavior test if the correction affects behavior.
- Large exploratory cases are laptop-resource-bound and opt-in; do not make a 100k-vector or million-row random workload the default local fuzz run. Never claim 100% performance path coverage from a finite random campaign; the pre-existing P01–P15 inventory remains the coverage contract and gets extended when fuzzing finds a genuinely new hot path.

## 4. Work packages (minimal overlap)

**F0 — All red BDD acceptance scenarios first.** Own `tests/features/fuzz/**` and synthetic expectations for schema validation, novelty, exact replay, independent oracles, bug dedup/reporting and performance promotion. Commit these **before writing any harness/production code**, execute them and record which expected unmet behaviors fail and why. Existing passing protections count as green controls; don't invent false failures.

**F1 — Allowlisted offline harness and deterministic replay.** Own `scripts/fuzz.py`, `fuzz/scenario.schema.json`, `fuzz/generators.py`, `fuzz/oracles.py` and the small Hypothesis development dependency/lock update. Implement safe input materialization, execution sandbox, invariant registry, shrink/replay and structured local reports. Neither invokes an AI nor changes financial product behavior.

**F2 — Local agent instructions and novelty tracking.** Own `docs/agent-fuzzing.md`, `fuzz/novelty.py` and an ignored local campaign-history format. Provide the strict AI scenario-authoring contract, novelty enforcement, coverage history, sanitized portable history export and explicit fresh-run operator workflow. No GitHub Actions modifications.

**F3 — Performance triage and bug-to-regression promotion.** Own the adapter to `scripts/perf.py`, `fuzz/triage.py`, plus small additions to existing `docs/performance.md`/`README.md`. Reproduce same-input local comparisons, generate portable redacted reports, minimize confirmed performance cases, and **promote deterministic cases** into the existing benchmark inventory. No new CI runner; ordinary CI picks up newly committed stable benchmark cases/tests under existing jobs.

**F4 — Confirmed bug fixes and full verification.** Own *only* modules implicated by confirmed findings and their minimized behavioral tests. For each defect: **red BDD test → targeted fix → green replay → complete correctness suite → affected P01–P15 benchmarks**. No broad speculative rewrite. Document what is and is not part of CI.

**Sequence:** `F0 → F1 → F2 → F3 → F4`. Preserve the original prerequisite PRDs; no agent-generated campaign may modify an irreplaceable ledger or run automatically. All harness verification uses synthetic fixtures in Docker, with no host dependency installation.

## 5. Behavioral acceptance scenarios (all written before implementation)

| ID | Given / When / Then observable contract |
|---|---|
| **AFZ-01** | **Given** a user has not requested fuzzing, **when** a PR is opened or CI runs, **then** no AI generation or fuzz campaign is triggered and no fuzz secret is needed. |
| **AFZ-02** | **Given** a local agent is asked for a new campaign, **when** it supplies cases, **then** the runner requires 12 distinct inputs, five workflow families, four stateful sequences and two performance cases. |
| **AFZ-03** | **Given** cases differ only by seed or narrative, **when** novelty is checked, **then** they cannot satisfy the 25% *structural* novelty quota. |
| **AFZ-04** | **Given** 12 genuinely distinct cases with three unseen shapes, **when** validated against previous campaign history, **then** the campaign is accepted and its hashes/coverage are stored. |
| **AFZ-05** | **Given** an input with shell commands, unsafe file paths, unsupported operations or oversized payloads, **when** validated, **then** it is rejected without executing anything. |
| **AFZ-06** | **Given** a valid but intentionally incomplete financial record, **when** evaluated, **then** it reports a typed incomplete/blocked outcome without fabricated basis or a financial mutation. |
| **AFZ-07** | **Given** inconsistent shares, tax-lot basis and activity chronology, **when** tested, **then** independent accounting invariants flag a wrongly accepted state. |
| **AFZ-08** | **Given** equivalent independent input rows in different orders, **when** processed, **then** authoritative substantive output is unchanged. |
| **AFZ-09** | **Given** a multi-operation bug, **when** minimized and replayed offline, **then** the smaller saved sequence fails in the same observable way on two clean runs. |
| **AFZ-10** | **Given** invalid user input that correctly fails, **when** fuzzed, **then** its expected structured error is marked as passing and the DB remains unchanged. |
| **AFZ-11** | **Given** a reproduced defect, **when** reporting completes, **then** the local report contains one deduplicated finding, evidence and an agent-free reproduction command. |
| **AFZ-12** | **Given** different newly generated datasets, **when** timed, **then** the tool does not compare their raw elapsed times as a candidate/reference regression. |
| **AFZ-13** | **Given** the exact same saved dataset measures 1,000 ms on reference and 1,260 ms on candidate twice, **when** locally compared, **then** a confirmed 26% performance regression is reported. |
| **AFZ-14** | **Given** a reproducible slow case, **when** promoted, **then** the existing fixed benchmark inventory includes its stable input and future CI exercises it **without** any AI fuzzing. |
| **AFZ-15** | **Given** a confirmed bug about to be fixed, **when** development begins, **then** a minimized Given/When/Then regression test is observed red before production changes and green after. |
| **AFZ-16** | **Given** five completed local campaigns, **when** history is inspected, **then** coverage of P01–P15 is reported honestly and any uncovered families are explicitly identified. |
| **AFZ-17** | **Given** agent failure, insufficient novel cases, timeout or a missing post-bootstrap history index, **when** campaign validation finishes, **then** it reports an actionable failure rather than silently substituting old cases or claiming completion. |
| **AFZ-18** | **Given** no external publishing approval, **when** a bug report is generated, **then** it remains local and no GitHub issue is posted. |

Use fixed synthetic fixture JSON and deterministic checker outputs to test novelty, comparator math, reporter contracts and failure handling. **No tests invoke a live AI service.** The live agent's actual ability to create novel scenarios is demonstrated in one **human-invoked local acceptance session**, with a saved sanitized manifest. CI may execute deterministic harness contract tests and promoted regressions as conventional tests, but never performs this session.

## 6. Completion criteria

1. An operator can request an **AI-designed, structurally novel** local fuzz campaign, inspect 12+ scenarios across the agreed families and obtain exact saved case artifacts and a sanitized, actionable report. Repeated input hashes and insufficient new structural shapes are rejected against available local history.
2. The campaign runs with synthetic data only, disposable isolated databases, bounded resources and no external network. The agent cannot supply executable code, expected financial calculations or overrides that make a failing assertion pass.
3. Confirmed defects are reproduced twice, minimized and recorded. Fixes occur only after a newly observed-red BDD case; complete behavior tests and affected benchmarks pass afterward.
4. Pathological performance findings are locally paired against **identical inputs**, then profiled and corrected. New critical workloads are promoted to **deterministic CI benchmarks** and inherit the original **>25%** relative regression gate; raw timing across different random cases never fails CI.
5. **No CI fuzz campaign exists.** Opening PRs, pushing to `main` or running scheduled/required checks never invokes the agent or generates new fuzz inputs. CI remains responsible for fixed BDD, fixed performance tests and stable previously-discovered regressions only.
6. Agent instructions, local campaign/replay instructions, coverage history semantics, data privacy boundaries and promotion workflow are documented. Original Unified MVP and performance PRDs remain otherwise unchanged.

**Result:** A human can ask an AI agent to invent genuinely new ways to break Investobot, obtain precise reproductions and prioritizable bug reports, and permanently guard against confirmed bugs and slowdowns **without introducing flaky, expensive or credential-dependent AI fuzzing into CI**.
