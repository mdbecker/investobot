**Date:** 2026-10-12

**Applies to:** `docs/PRD-unified-mvp-2026-10-10.md`, `docs/PRD-performance-ai-fuzz-2026-10-10.md`, and their earlier performance/fuzz attachments. **This addendum supersedes conflicting benchmark, fuzz-campaign, timing, and evidence-retention requirements only.** All substantive MVP financial correctness, safety, agent workflow, and data provenance requirements remain in force.

## 1. Product goal and priority order

Investobot is a **single-user, laptop-local, long-term, passive-fund portfolio assistant**, not an enterprise trading or benchmark platform. **Deterministic Python CLI** owns financial facts, math, tax rules, validation and reproducible reports; **small, composable AI agent skills** own browser research, evidence collection, orchestration and explanation. No broker credentials, broker trading, autonomous investment decisions, or background agent service. Target monthly contribution investing and at most quarterly routine rebalancing, with explicit human approval.

Prioritize in this order: **(1) correct/traceable ledger and safe recovery; (2) trustworthy import from real brokerage documents; (3) actual returns and tax-lot/yearly tax-dollar accounting; (4) exact human-reviewed contribution, rebalance and TLH proposals; (5) fund discovery, historical target comparison and complete/unknown recursive look-through; (6) portfolio-wide research and reusable agent skills; (7) measured speed and optional semantic retrieval.** Never declare a performance milestone complete at the expense of any higher priority.

Before first *real* financial use, demonstrate the original nine workflows end-to-end: HTML → accepted account facts and actual returns; tax-budget rebalance; specific-lot TLH; comparable substitute funds; screening to user criteria; full nested underlying holdings; political-contribution research on top-N underlying companies; news-impact research across held companies; and target/backtest/transition reports with a **yearly estimated-tax-cost** limit. Each workflow must either return a dated, sourced, numerically consistent, human-reviewable result or **block clearly with typed reasons**. The agent must not invent missing basis, dates, exposure, prices, legal conclusions or annual tax availability. Synthetic-only demos do not satisfy real-data validation.

## 3. Replace the oversized performance framework with a practical one

Keep **one** simple reproducible performance runner and **eight representative, stable workflows**: (1) portfolio performance/TWR–XIRR; (2) tax lots and annual tax-budget calculation; (3) contribution-first proposal and saved-plan list/report; (4) household TLH analysis; (5) recursive fund look-through/top issuers; (6) ten-year strategy backtest; (7) SQLite/DuckDB historical analytical query; (8) research corpus text/vector retrieval or portfolio research aggregation. Each benchmark requires a fixed, small-to-medium synthetic fixture, verified result/count/hash, and clear measured boundary. Coverage means these representative expensive **workflows**, not every command or every code path; add a benchmark only after a new real hot path is demonstrated. Keep correctness, missing-data, permissions, backup/restore and migration tests in the **ordinary BDD suite**, rather than timing everything.

For trusted CI, compare **candidate with the one pinned reference on the same runner**, using one warm-up and **five** samples; the median must fail for a **confirmed >25% increase** after one complete confirmation measurement. Batch sub-200-ms operations so noise does not dominate; an invalid measurement fails clearly, not as an alleged slowdown. Retain only metrics genuinely useful for the case (time; memory or on-disk growth when relevant). Publish concise per-case results; there is **no three-revision requirement, mandatory 21-sample p95, universal 1×/4× scaling, 114-case inventory, 20/60-minute aggregate timing certification, or 100k-vector CI obligation**. Run optional larger diagnostic/stress tests locally when justified; failure of an unrealistically sized synthetic stress case is not by itself an MVP blocker. Preserve the 25% guard, meaningful correctness checks and deterministic replay.

**Do not optimize brokerage HTML parsing/import further now.** Its institution profiles and vendor data have not been verified against representative real anonymized pages. Remove import stress/scaling/absolute-latency gates from MVP acceptance; retain import **functional** tests for source chronology, value reconciliation, stable lot identities, account isolation, atomicity and idempotence. Keep already-landed import optimizations **only if** focused behavioral tests pass and review shows they are straightforward, smaller/clearer, and do not create stale caches or ambiguous semantics; otherwise revert the optimization-specific complexity. Revisit import performance after real source validation reveals a user-visible problem.

**CI safety:** Run fixed performance jobs on appropriately isolated/trusted runners. Do **not** execute untrusted pull-request code on a personal self-hosted runner with the Docker socket mounted. Prefer ordinary GitHub-hosted isolation for PR performance checks; use the M4 only for explicitly trusted, on-demand diagnostics. Do not claim a required performance gate is operational until an actual complete job passes and the repository enforces the intended check. AI fuzz campaigns are never part of CI.

## 4. Git hygiene and size reduction

Remove **generated timing/profiling outputs and interrupted-run JSON** from the current tracked tree (not from Git history). In particular, prune `docs/performance-evidence/**` bulk artifacts and other generated benchmark reports; add these output paths to `.gitignore` and `.dockerignore`. Keep only compact benchmark definitions, reproducible fixture recipes, a short summary with key source SHA/fixture hashes/results and any **minimal** fixtures needed to demonstrate a specific bug. Archive large evidence outside Git, for example in local ignored data or CI artifacts with an explicit retention policy; do not silently discard evidence needed to investigate an open correctness issue. **No history rewrite, Git LFS, new storage service or repository-wide file reorganization.** Simplify the ~10k-line benchmark scripts/configuration where code is now duplicative; avoid arbitrary line quotas and preserve tested behaviors.

## 5. Make AI fuzzing a lightweight, useful agent skill

**Only on explicit human request**, the agent reviews the current code, previous findings and invariants; invents **new, varied, adversarial** input/state/event sequences; runs them offline against disposable synthetic ledgers; explores surprising results or slow paths; reproduces/minimizes actual defects; and writes a concise bug report with command/input, expected vs observed result, affected invariant, source version and severity. Keep replayable seeds and minimized examples. **No required number of scenarios, novelty percentages, five-campaign quota, per-family coverage matrix, hosted provider, automated GitHub issues or standing fuzz scheduler.** Existing `fuzz/` modules may be consolidated or removed if a short agent skill plus small replay script provides the same useful behavior; don't build another general framework.

For every confirmed bug, **write and observe a failing domain-language BDD test first**, implement the smallest safe correction, replay the reproducer and make the full correctness suite green. For slow-path findings, record a reproducible matched-input profile; promote only consistently important cases into the small fixed performance suite. CI runs **only** deterministic promoted regression tests, never AI-generated campaigns. An exploratory run that finds no bugs is acceptable and should say so, including what was exercised.

## 6. Cleanroom code-quality review — keep the good foundation

Use the original review's **intent → architecture → implementation → polish** order and its specific findings, guided by `code_review(8).md` and `code_smell_review(9).md`. Focus on **Bloaters, Change Preventers, Dispensables and Couplers** in the touched code: duplicated SQL/serialization, oversized methods, speculative adapters, redundant registries, unused compatibility scaffolding, excessive test fixtures, repeated business rules and verbose status docs. Prefer the smallest cohesive domain functions and **one authoritative data/CLI contract**, not more wrappers, plugins, services, ORM layers or parallel test harnesses. Remove dead code and duplicated documentation. Keep useful typed statuses, Decimal arithmetic, transactions, exact lot/event identities, source provenance, known/unknown distinctions, immutable plans, safe backup/restore and reviewed source permissions. As the project has **no real users/data yet**, do not preserve dead legacy compatibility just to satisfy old snapshots; however, **do not destroy any real ledger if one now exists**. Preserve forward schema-versioning and tested future migration/backup capability.

BDD tests describe observable user outcomes, not internal read counts, mocks of internal collaborators or line-specific call ordering. When refactoring without changing behavior, existing green correctness tests are valid safeguards: do **not** manufacture failing tests. Write red-first scenarios for genuinely missing behavior or a reproduced bug. A green synthetic test suite does not prove broker parser accuracy, live market-provider availability, legal wash-sale suitability or real-world performance.
